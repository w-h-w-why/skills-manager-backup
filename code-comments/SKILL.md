# code-comments —— 注释即交接契约

从本文件生效起，本项目里**任何一次代码改动**都同时是两件事：改行为，以及把理解写进代码。注释不是交付物的包装，而是交付物的一部分。

## 为什么（读一次，记住它的立场）

注释的读者有两个：坐在 diff 前的人，和**下一个**改这段代码的 agent —— 它没有你的会话记忆，没有你的推理过程，它读到的代码加注释就是它的全部上下文。所以一条注释的验收标准只有一句：

> **读它的人，能知道一段源码本身说不出口的事。**

说不出口的是：为什么这样做、约束来自哪里、边界上会发生什么、改动这里会连带影响什么。只把代码已经明说的东西换个说法写一遍，等于没有注释，反而增加噪音——这是本 skill 重点反对的做法。按这个标准写，两个读者同时受益：人类审查时看得到设计意图，下一个 agent 接手时不需要重新推演一遍。

## 核心原则

1. **说 why，不说 what。** 任何能被代码本身读懂的句子都不写。每一条注释都要通过上面那句验收标准。
2. **注释跟代码同步迁移。** 改了行为，包含被改代码的文件里，所有相关注释（模块头、函数文档、行内说明）在同一批改动里更新。留下过时的注释比不写更糟：它把下一位读者引向错误的理解。
3. **宁可多写，不可少写。** 除非项目有明确规则反对注释，或仓库里的既有风格确实极度精简，否则不担心"注释太多"。多写只是冗长，少写会让下一个人重新推演。
4. **契约稳定，实现可变。** 注释写行为契约与理由，不写具体实现路径；实现会变，写死实现细节的注释会立刻过时。
5. **语言跟随项目。** 中文说明配英文术语原形（lock、backoff、idempotent……）；若项目已有英文注释惯例，全部用英文。技术名词不翻译。

## 注释层级清单

对每个新增或修改的单元，逐层对照。**每一个新增/修改的函数、类、模块都要有注释**，行内说明则按"是否需要"判断。

### 模块 / 文件头

文件的职责、它在系统里的位置、与其他模块的边界。只在关键处讲，不逐个复述文件里的函数。

```python
"""订单结算核心：把购物车转成可支付的订单。

职责边界：只负责金额计算与状态置位，不关心支付渠道；渠道调用在
billing/channels 里。金额一律用整数分表示，避免浮点误差（对齐
上游 payment API 的字段单位）。
"""
```

### 类

职责、使用场景、生命周期与初始化要求、并发/线程安全性，以及为什么它被设计成这样。这是理解一个类的入口。

```python
class OrderDraft:
    """下单过程中的可变草稿。

    在用户点"提交"之前持有中间状态，提交时冻结成不可变 Order。
    非线程安全：一个草稿只在一个请求上下文中使用，不要跨请求共享——
    共享会让并发提交看到彼此的中间状态。
    """
```

### 函数 / 方法

必须覆盖四件事，缺一不可：

- **意图**：它替调用方解决了什么问题
- **参数**：每个参数的含义、单位、取值范围、可选时的默认值语义
- **返回值**：返回什么；无返回值时说明通过什么途径产生效果
- **边界与错误**：输入为空/越界/并发时怎么表现；抛什么异常；什么情况返回 None
- **副作用与前置条件**：网络调用、写库、锁、重试

复合参数与不变量（invariant）写进 docstring，不藏在行内，保证只读函数签名就能判断能不能用。

### 复杂逻辑

每个非显而易见的判断、循环、锁、算法或设计选择，就近说明**为什么这样写、为什么是这个顺序、为什么不能用看起来更自然的写法**。这是最容易漏掉、也最影响接手者的一层。

```python
# 先用窗口起点排序：写进 ledger 的顺序决定重放结果，
# 乱序会让审计重放产生与线上不一致的余额（见 ledger.md）。
for entry in sorted(entries, key=lambda e: e.window_start):
    ...
```

### 边界情况

显式标注已知边界：空输入、越界、并发、精度、时区、编码、超时退避。写下这个边界被有意处理的方式，以及为什么这么选。

```js
// 金额比较用容差：上游渠道按分取整，直接 === 在 0.1+0.2 这类
// 浮点累加后会误判为不相等。
const same = Math.abs(a - b) < 0.005;
```

### 设计原因

写下非显然的选择、被否决过的替代方案、以及代码里看不出来的依赖与约束。

```ts
// 用轮询而非 WebSocket：网关限制单连接数，且这个接口每 30s 才更新一次，
// 长连接的成本和复杂度都不值得。若未来改成推送，删掉这个定时器即可。
```

## 反面示例：看似详尽、实则浅薄

这是本 skill 主要要消灭的写法。左边不投入任何判断，右边才传递理解：

```python
# ❌ 自增计数器
i += 1

# ✅ 只在前 N 次尝试里重试：更晚的请求说明上游已经过载，
#    继续重试只会加重拥塞。
i += 1
```

```js
// ❌ 遍历所有用户
for (const user of users) { ... }

// ✅ 顺序处理而非 Promise.all：下游限流 10 QPS，
//    并发会触发 429 并让整批失败。
for (const user of users) { ... }
```

```python
# ❌ 返回 None
return None

# ✅ 返回 None 表示"钱包不存在"，与"余额为 0"区分开：
#    调用方对两者要采取不同动作（前者建钱包，后者直接扣款）。
return None
```

判据：**把注释删掉，下一位读者（人或 agent）会不会丢失信息？** 不会 → 删掉重写或换一种写法；会 → 留下。

## 改代码时：同步已有注释（最容易漏的一步）

改动前先读改动点**周围**的注释，改动后逐一核对：

- 行为变了 → 对应注释必须重写，而不是留着"大部分还对"的版本
- 参数、返回值、异常集合变了 → 函数文档同步更新
- 发现了与代码不符的旧注释 → 顺手改对；确认不了原意图的，把可疑之处作为问题提出来，不要默默改成自己的理解
- 删掉代码 → 连带删掉只服务于它的注释；一个模块被删空后，文件头说明也要更新

**只增不改不算完成。** 一份新写的漂亮注释盖在过时的旧注释旁边，下一位读者无法分辨哪个是真的。

## 写完之后：必做核对（这是完成判据）

在报告"完成"之前，逐项过一遍，并把结果写进你的汇报：

1. **逐个点名**：本次改动新增/修改的每个函数、类、模块，是否都有对应层级注释——尤其是函数文档里意图/参数/返回值/边界四件事齐不齐。不能只说"已加注释"，要点到每一个单元。
2. **每个复杂逻辑块**：是否说明了理由（why），而不是复述行为（what）。
3. **同步性**：改动区域内是否还有与新行为矛盾的残留注释。
4. **粒度合理性**：有没有把明显的代码（`i += 1` 上的"自增计数器"）也写了注释；有则删掉或改写为说明 why。
5. **风格一致**：注释语言与格式是否符合本文件所在项目的既有惯例。
6. **逐 hunk 过一遍 diff**：每个改动块要么有注释说明其意图，要么它确实足够自明。给不出理由的块就是漏的。这一步没有做完，改动就还是未完成状态。

## 不适用

- 生成文件（`*.pb.go`、生成的 schema、lock 文件）和第三方 vendored 代码：不改，也不往上加注释。若要改，改生成源。
- 判断某个文件属于生成物：看文件头标记、仓库 README、生成脚本配置；不确定就先问，别先写。
- 一次性脚本、REPL 试验、throwaway 原型：写清用途与关键假设即可，不追求本文的完整规格。
- **项目自身规则优先**：若仓库的 lint 规则或 AGENTS.md / CLAUDE.md 明确要求精简注释，遵从项目规则，并在汇报里说明你按项目规则放宽了哪些要求。这条只在项目明确表态时生效，不能拿"看起来像这个风格"当理由跳过。
