# vibecoding-docs

让项目文档成为可信的上下文：需求说明目标，代码描述实现，ADR 保存决策，TODO 和进展记录帮助接续工作。文档更新属于开发工作的一部分，无需用户每次提醒。

## 入口与模式

| 情况 | 执行路径 |
| --- | --- |
| 要求初始化文档；项目首次开发；接手项目发现必要上下文缺失 | 读取 [初始化流程](references/initialization.md)，按项目事实建档 |
| 要求更新某个文档或记录一次变更 | 读取 [维护流程与写入时机](references/maintenance.md)，只处理相关事件 |
| 功能、修复、重构、测试、配置或脚本发生修改 | 自动执行 [开发巡检](references/maintenance.md#开发巡检)：每批修改后、验证产生新变化后、交付前 |
| 要求检查文档是否过期、重复或矛盾 | 执行下方审计流程 |
| 不确定信息归属或是否需要独立文件 | 读取 [文档职责](references/doc-contracts.md) |

任何代码修改都要检查；纯格式或注释变化若没有改变文档事实，检查后不必写入。用户明确只要建议或目录清单时，输出建议，不因此修改项目。

## 事实与权限

- 修改前读适用的项目指令、相关文档和当前工作树。Git 项目用 `git status --short`、适当的 `git diff`/`git diff --cached` 区分已有改动和本次工作；非 Git 项目按实际读写过的文件检查，不凭空重建历史。
- 对照当前文件、配置、接口和相关测试，不能仅凭任务描述、记忆或 diff 推断最终状态。适用的子目录指令也要读取。
- 用户确认的需求与明确规则是约束；代码是当前实现的证据。两者冲突时按维护流程判断，不能一概以代码为准。
- 沿用现有路径、命名与内容。局部补齐和已授权的事实同步直接完成；用户要求整体重组时按该授权执行。无关的搬迁、删除、重写或更改约束不属于自动同步。
- 信息放一个主文档，其他地方引用。先找已有的 README、CONTEXT、ROADMAP、ADR、接口规范等对应入口，避免为新名称另建一套内容。
- 项目文档中的文件引用、源码引用、索引和目录导航使用可点击的 Markdown 链接，按所在文档计算相对路径。真实目录导航使用带链接的列表；尚未创建的文件写明待创建，不添加死链。具体规范见 [链接与导航](references/maintenance.md#链接与导航)。
- 现状说明原地更新；历史事件保留；规范变更记录授权和原因。未知事实写清待确认点，不用模板示例或猜测填充。
- 单独建档、审计或文档更新不扩展为代码修复。开发任务本身包含修复时可以继续在该范围内处理，并同步文档。

## 将自动维护写入项目

初始化，或首次在一个已授权开发/文档维护的项目中应用本 Skill 时：

1. 将 [维护流程与写入时机](references/maintenance.md) 作为项目 `docs/doc-maintenance.md` 的初始内容，适配触发表中的实际文档路径，主文档列按目标文档的位置生成已存在文件的 Markdown 链接。已有等价维护规则时就地补齐，保持唯一入口。
2. 用 [AGENTS 维护小节模板](assets/AGENTS-doc-maintenance.template.md) 局部增补项目 `AGENTS.md`，将链接适配实际路径。保留所有既有规则；已有同等小节时只补缺项。没有 AGENTS.md 时新建精简文件。
3. 用户要求更新单份文档而范围不含项目规则时，完成那份文档，不额外安装上述规则。只读审计也不写入规则。

维护文件必须先创建，再加入导航链接。它与 AGENTS.md 是后续开发的持久入口；Skill 元数据保持自动调用开启。

这定义遵守项目指令的 Agent 的默认工作流程。Skill 本身没有后台文件监听，也不能强制不读取项目指令的工具执行检查；本任务不安装钩子、CI 或修改全局配置。

## 审计

先读取 [文档职责](references/doc-contracts.md) 和 [维护流程](references/maintenance.md)，再检查：

- 文档是否对应当前命令定义、模块边界、API/模型、配置读取方式和部署事实。
- 明确需求、非目标、业务规则、依赖方向等约束是否被代码违反。
- 是否有重复的主文档、互相矛盾的说法、死链、不存在的文件、不可跳转的文件引用或未经验证的命令。
- TODO 是否与已实现且已验证的状态一致；记录是否重复；现状和历史是否混写。
- 是否缺少承载实际需求的文档，或存在只有标题和示例的空文档。

只要求审计时输出发现和修复建议；用户要求检查并修复时，在授权内直接修正文档过期和链接问题。规范冲突按维护流程立即提出，不改写约束以掩盖冲突。每条发现带文件位置、证据、影响和建议。

## 完成标准

交付前必须有这四项证据：

1. 本次代码/配置改动的相关文档均已检查，检查依据包含当前实现。
2. 每个命中的写入时机已更新对应文档，或有明确的无需写入理由；相同事件没有重复记录。
3. 新增或更改的路径、链接、命令与事实已核验；实际运行和未运行的检查分开报告。
4. 冲突已经解决，或已即时提出并明确保留待裁决状态。未验证任务不标为完成，仍有未同步文档时继续同步。

最终简要报告：代码触碰范围 → 检查和更新了哪些文档 → 验证证据 → 冲突/待确认项。无文档变化时写明“已检查相关代码与文档；本次没有改变文档事实”。
