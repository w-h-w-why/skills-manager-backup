# vibecoding-docs：文档职责边界

本文定义每份文档的唯一职责、事实来源和写入方式。持续更新的触发表与操作步骤见 [maintenance.md](./maintenance.md)。

## 三类信息

### 现状型

描述系统现在是什么：`README.md`、`architecture.md`、`context.md`、`data-model.md`、`api.md`、`setup.md`、`testing.md`、`glossary.md`。代码、配置、目录和可复现验证是主要事实来源；实现改变后原地修正，删除被推翻的旧描述。

### 规范型

规定应该怎样做：`AGENTS.md`、PRD 中的范围和非目标、`context.md` 中的业务规则、架构中的依赖边界、`security.md` 中的安全要求。代码偏离规范时先报告冲突，不能为了让检查通过而默默改规范。

### 记录型

描述发生过什么：`CHANGELOG.md`、`docs/adr/`、`docs/notes/progress.md`、`docs/notes/known-issues.md`。保留历史；ADR 和进展带日期，未发布 CHANGELOG 按变更类型整理。旧决策被取代时新增 ADR；原 ADR 只更新状态或取代指向，known-issues 可更新状态和解决证据，progress 同一任务条目可补充。

## 文件职责表

| 文件 | 唯一主责 | 不写入 |
|---|---|---|
| `README.md` | 项目定位、快速开始、入口导航 | 完整业务规则和历史过程 |
| `AGENTS.md` | Agent 的命令、边界、检查门槛 | 大段架构说明和事件流水账 |
| `TODO.md` | 当前待办、进行中、验收条件 | 已完成工作的完整历史 |
| `CHANGELOG.md` | 面向用户的版本变化 | 临时调试过程 |
| `.env.example` | 环境键名、占位值、用途提示 | 真实密钥和真实账号 |
| `docs/README.md` | 文档导航与主题入口 | 已有主文档的完整副本 |
| `docs/prd.md` | 目标、用户、范围、验收 | 实现细节和代码快照 |
| `docs/context.md` | 领域概念、业务规则、状态语义 | 技术选型历史 |
| `docs/architecture.md` | 当前模块、数据流、依赖边界 | “曾经如何设计”叙事 |
| `docs/data-model.md` | 实体、字段、关系、约束 | 与数据无关的业务愿景 |
| `docs/api.md` | 接口契约、错误、认证、版本 | 未实现的愿望接口 |
| `docs/setup.md` | 本地安装、初始化、环境准备 | 生产值班流程 |
| `docs/testing.md` | 测试层级、命令、验收方法 | 不可复现的口头保证 |
| `docs/glossary.md` | 术语、缩写、命名约定 | 架构决策理由 |
| `docs/adr/` | 重要决策的背景、选择和后果 | 当前事实的重复副本 |
| `docs/notes/progress.md` | 阶段进展和交接信息 | 稳定规范 |
| `docs/notes/known-issues.md` | 已知缺陷、限制、临时绕过 | 未确认的猜测 |
| `docs/security.md` | 威胁、权限、敏感数据约束 | 普通产品需求 |
| `docs/deployment.md` | 发布、部署前提、回滚步骤 | 凭空推断的生产操作 |
| `docs/operations.md` | 部署后监控、备份、故障处理 | 本地安装步骤 |
| `docs/doc-maintenance.md` | 本项目触发表、巡检和冲突流程 | 产品功能描述 |

| `LICENSE` | 授权条款 | 项目使用说明 |

## 推荐档位

小型项目至少有 `README.md`、`AGENTS.md`、`TODO.md` 和 `docs/doc-maintenance.md`；存在业务规则时加 `context.md`，存在测试时加 `testing.md`。中型项目加 `prd.md`、`architecture.md`、`context.md`、`setup.md`，按需增加模型、API、术语、ADR 和 notes。长期项目使用完整树，并按实际需要加入 `CONTRIBUTING.md`、`LICENSE`、安全和运维文档。任何档位都不创建空文档。

具体主目录与子目录关系见 [initialization.md](./initialization.md)；推荐文件名应适配现有项目，例如沿用根目录 `CONTEXT.md` 或既有 `docs/product/requirements.md`，不创建第二份权威副本。

## 易混淆的边界

- `context.md` 定义业务规则和状态含义；`glossary.md` 只解释词语及命名，两者用链接连接。
- PRD 的验收标准表达目标；实现是否已经达到标准要标明状态，不用当前缺陷降低标准。
- `data-model.md` 解释模型和约束；schema/迁移文件保存机器定义，文档链接到它们。
- `api.md` 解释接口契约；若存在 OpenAPI 定义，链接它并同步语义，避免手写第二套字段表。
- `setup.md` 解释完整开发准备；README 保留最短可用流程，命令变化时同时核对。
- `.env.example` 是环境模板；配置变化时与 setup 同步，不读取真实密钥填入文档。
- `architecture.md` 描述当前结构；ADR 解释选择原因，旧方案仅作为决策历史保留。
- TODO 表达下一步；progress 表达交接；CHANGELOG 表达已交付行为，不复制同一段事件。
- known-issues 保留问题证据、影响、绕过和解决状态；已有问题重复出现时更新条目而不重复新增。
- `AGENTS.md` 保留简短强制规则；完整触发表下沉到项目维护文档并链接。所有真实文件引用、索引和目录导航都遵守 [链接与导航规则](./maintenance.md#链接与导航)，推荐结构示例与实际导航分开。

## 各类文档的可检查完成条件

| 类别 | 写入结束条件 |
|---|---|
| 现状型 | 本次影响的行为均已核对，当前表述与已验证实现一致 |
| 规范型 | 已获授权的规则变更写明；未裁决冲突保留并上报 |
| 记录型 | 仅新事实产生新条目，日期真实，同一事件可唯一识别 |
| 导航型 | 真实文件引用可点击，链接与锚点可达，未创建文档没有占位死链 |
| 任务型 | 进行中状态与实际工作一致，完成项有验收依据 |

旧项目首次建档只能记下当前已证实状态；不得编造发布日期、过去决策或“已经通过”的测试记录。待确认项要明确缺少什么依据。

## 写入与冲突原则

1. 写前读取目标文件和当前工作树，避免覆盖已有改动。
2. 事实变化更新现状型文档；事件发生追加记录型文档；规则变化必须明确记录规范变更。
3. 同一信息只保留一个主文档，其他位置链接引用；重复运行时更新已有条目，不重复追加。
4. 代码与现状描述不一致时，以已验证的新行为修正文档；无法验证就标记待确认。
5. 代码与规范型文档冲突时，引用规范原文和代码位置，立即提出“改代码”或“正式改规范”的选择；未裁决前不默默降低约束。
6. 用户明确要求改变规则时可以更新规范，但应说明被推翻的原文；涉及架构取舍时新增 ADR。
7. 命令、路径、接口和配置先静态核对，运行验证仅限安全、可逆且不会写入真实外部系统的操作。
8. 交付报告必须说明本次改动、更新文档、未更新原因、冲突和未运行的验证。

具体触发表和完成检查见 [maintenance.md](./maintenance.md)。
